Contract vs Queue: What to use?

For transactional notification systems, you should almost always use a message queue + schema contracts — you don't have to choose one or the other!

Avoid only synchronous contracts (direct API calls):

  • Tightly couples core transactions to notification delivery
  • If your notification service is down, customer payments/orders can fail
  • No traffic spike buffering for sale days or mass alerts
  • Retries block your main application flow

Use a message queue (SQS, RabbitMQ, BullMQ):

  • Fully decoupled: notifications never break core transactions
  • Built-in retries, dead-letter queues, and rate limiting for SMS/email providers
  • Buffers traffic spikes automatically
  • Add new channels (Slack, push, etc.) without changing transaction code

Final recommendation: Use a queue for all customer-facing notifications, and add JSON schema contracts on queue messages to guarantee format consistency between producers and consumers. Only use direct synchronous contracts for critical internal admin alerts.
